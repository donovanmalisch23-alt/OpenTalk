# Feasibility and risk assessment

Likelihood and impact are rated High, Medium or Low. "Evidence needed" is what retires the risk. The highest risks are scheduled first in the [roadmap](roadmap.md).

| # | Risk | L | I | Mitigation | Evidence needed |
|---|---|---|---|---|---|
| R1 | **Real-time audio quality on Windows.** Qt Multimedia's `QAudioSource`/`QAudioSink` give limited control over buffer sizes, exclusive mode and loopback, and device-change handling varies by backend. | H | H | Hide audio behind an `AudioBackend` interface. Prototype with miniaudio (WASAPI) early in Phase 4 and compare with Qt Multimedia on latency, dropouts and device hot-plug. | Latency and dropout benchmark from the Phase 4 spike. |
| R2 | **Encrypting the audio path.** UDP needs DTLS or an AEAD scheme. Qt's `QDtls` is believed to need the OpenSSL TLS backend, while Qt on Windows defaults to Schannel. A custom scheme would conflict with "no invented crypto". | M | H | Prefer standard DTLS 1.2/1.3. Fall back to a well-documented construction (keys exported from the TLS 1.3 control session plus libsodium AEAD with a replay window) only after a written security review. Decision recorded in an ADR before Phase 4. | Working DTLS prototype on Windows; or review notes for the alternative. |
| R3 | **Screen reader behaviour of Qt widgets.** Qt exposes UI Automation on Windows. NVDA support for Qt trees, lists and dynamic content has had gaps historically. Live announcements need `QAccessibleAnnouncementEvent`, which only exists in Qt 6.8 and later. | M | H | Use Qt 6.8 LTS or later. Prefer standard widgets. Automated checks for names and roles; manual NVDA script for each release candidate; custom `QAccessibleInterface` only where testing shows a need. | NVDA test script results on the Phase 1 build (owner can run this now). |
| R4 | **Plugin isolation.** In-process C++ plugins run with the full privileges of the application, so capability declarations cannot be enforced against them. | H | H | Two tiers. Out-of-process plugins talk through a restricted IPC API (the default for third-party plugins). In-process plugins are allowed only for first-party, real-time audio effects. The UI states the difference honestly. | Phase 6 IPC prototype; overhead measurements. |
| R5 | **System-audio sharing.** WASAPI loopback captures a whole output device, so voices from OpenTalk itself are captured too and loop back. Per-process loopback needs a recent Windows (build 20348 or later, effectively Windows 11). A real virtual audio cable needs a kernel-mode driver, signing through Microsoft Partner Center and an EV certificate. | H | M | Phase 7 starts with per-process loopback that excludes OpenTalk's own process. Whole-device loopback is offered only with an explicit warning and OpenTalk output routed to a different device. A driver is out of scope unless the owner approves its cost. | Phase 7 research report. |
| R6 | **Public-internet hosting.** Carrier-grade NAT, missing port forwarding and certificate setup will stop many hosts. | H | M | Clear diagnostics, a reachability self-test, and documentation. Trust-on-first-use certificate pinning so self-signed certificates are workable. No mandatory relay. | Phase 8 testing on residential connections. |
| R7 | **Licensing.** Qt is LGPLv3/GPL, Opus is BSD, OpenSSL is Apache-2.0 and libsodium is ISC, all compatible with GPL-3.0-only. Remaining risks are TeamTalk soundpacks (not redistributable without permission), codec patents (Opus has a royalty-free patent licence), and any GPLv2-only dependency (incompatible). | M | M | [Third-party register](licensing/third-party-register.md) enforced in review; original soundpacks. Get legal advice before the first public binary release. | Register complete for each release. |
| R8 | **Scope.** The full specification is several person-years of work. | H | H | Vertical slices with exit criteria; [status.md](status.md) is the honest progress record; features not started are hidden, not shown as dead buttons. | Phase exit reviews. |
| R9 | **Moderation abuse and owner lock-out.** | M | M | Non-delegable owner capabilities, an offline owner-recovery command that needs file-system access, and a hash-chained audit log. Limits are documented: a server owner with disk access can still rewrite history. | Phase 5 tests for privilege escalation and lock-out. |
| R10 | **Windows 10 support.** The owner chose Windows 10 as the minimum. Its consumer security updates from Microsoft ended in October 2026, and its built-in TLS (Schannel) has no TLS 1.3. Future Qt releases may drop it. | M | M | OpenSSL ships with OpenTalk, so TLS 1.3 works on Windows 10 ([ADR 0007](architecture/decisions/0007-openssl-tls-backend.md)). Stay on a Qt LTS that supports Windows 10, and test on Windows 10 before each release. | Release testing on Windows 10 22H2. |
| R11 | **Single-maintainer bus factor.** | M | M | Documentation-first, ADRs, CI that a newcomer can rely on, and contribution guides. | — |

## Feasibility conclusions

- **Feasible with standard tools:** the client UI, the settings and storage layer, the TLS control protocol, server state, the permissions and moderation logic, Opus voice, the headless server, and out-of-process plugins.
- **Feasible, but must be proven by a prototype before committing:** a low-latency audio backend (R1), audio encryption (R2), and NVDA behaviour of the channel tree and live announcements (R3).
- **Expensive, needs an explicit owner decision:** a custom virtual audio driver (R5), and code-signing certificates for releases (also affects SmartScreen warnings).
- **Explicitly not promised:** end-to-end encryption. It conflicts with server-side moderation, recording and bots, and needs separate key management. It is listed as a future research item only.
